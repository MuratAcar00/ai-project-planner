# Shift Coverage

Zero-dependency Node.js CommonJS service (Node 22 or newer). Run `npm start` to listen on `127.0.0.1:3000`; `PORT` optionally changes the port. Run `npm test` and `npm run build` for verification. No installation is needed.

From the project directory:

```sh
node --version
npm test
npm run build
npm start
```

Open `http://127.0.0.1:3000` in a modern browser with JavaScript enabled. Stop the server with Ctrl+C. If port 3000 is occupied, use `PORT=3001 npm start` in a POSIX shell and open port 3001 instead. The workspace must be writable so the first saved change can create the data directory. No accounts, credentials, external services, or dependency installation are required. The build command checks syntax; there is no compilation step.

`createServer({ dataFile })` from `src/app.js` returns an unlistened HTTP server. The default JSON file is `data/coverage.json` inside the workspace. Tests inject isolated storage beneath `test/`. Storage uses atomic replacement, validates records on startup, and fails on corrupt data without overwriting it. Run one server process per data file; this store does not coordinate multiple processes.

## API

All request bodies use `Content-Type: application/json` and are limited to 16 KB. Responses are JSON except the plain-text summary. Errors use `{ "error": "message" }` with 400 for validation, 404 for missing resources, 405 for unsupported collection methods, 409 for domain conflicts, 413 for oversized bodies, 415 for unsupported media types, and 500 for internal errors.

- `GET /api/health` returns `{ "status": "ok" }`.
- `/api/events`: fields `name` (required), `location` (optional).
- `/api/volunteers`: field `name` (required).
- `/api/shifts`: fields `eventId`, `title`, `startsAt`, `endsAt`, `capacity` (all required). Times must be ISO timestamps with timezone; end must follow start. Capacity is an integer from 1 to 1000.
- `/api/assignments`: fields `shiftId`, `volunteerId` (required). Each volunteer can be assigned once per shift; assignments cannot exceed capacity.

Each collection supports `GET` (array) and `POST` (create, status 201). `/api/{collection}/{id}` supports `GET`, `PATCH`, `PUT`, and `DELETE` (status 204). Both update methods merge supplied fields. IDs are generated by the server. Unknown fields are rejected; text fields are trimmed and limited to 200 characters. Each collection is limited to 10,000 records.

Deleting an event deletes its shifts and their assignments. Deleting a shift or volunteer deletes its assignments. Capacity cannot be reduced below the assigned count.

`GET /api/coverage` returns shifts ordered by start time with `assigned`, `uncovered`, and `covered` fields. `GET /api/summary` downloads a concise UTF-8 text summary with shift times, counts, gaps and volunteer names. Both accept optional `?eventId=...` filtering. Display text with `textContent` in consuming clients; the API never renders user text as HTML.

## Organizer dashboard

Open `http://localhost:3000` after starting the server. Create an event, add shifts with local start/end times and capacity, add volunteers, then assign them to shifts. Edit shifts or remove assignments as plans change. The event selector scopes coverage counts, the gap filter and the downloaded summary. Volunteer names are shared across events. The dashboard starts empty and uses only saved API records; no sample data or remote assets are loaded. Failed requests show an error and loading can be retried. Layout adapts to mobile screens, forms have accessible labels and dialogs support keyboard navigation.

Coverage readiness shows filled spots as a proportion of total capacity, with per-shift progress and text labels for open spots. Use **Edit event** to update the selected event name or location. Empty states guide first-time setup. During loading or a failed refresh, stale dashboard controls are disabled until a successful retry; overlapping refreshes keep only the newest result.

The test suite includes API workflows and dependency-free dashboard logic checks for loading recovery, out-of-order refreshes, coverage filtering, and safe text rendering. These logic checks do not replace visual or assistive-technology testing in a browser.

Tests also cover domain validation and capacity limits, deletion cascades, event-scoped summaries, storage round trips, corruption rejection, and rollback after failed mutations or writes. Each storage test uses an automatically cleaned temporary directory under `test/`; tests never open the default production data file. Real HTTP tests bind an ephemeral loopback port and explicitly skip only when the environment denies listening (`EPERM` or `EACCES`). Simulated API tests remain available in those environments.

## Architecture

- `src/server.js` validates the port and starts the loopback listener.
- `src/app.js` exports `createServer(options)`, routes built-in HTTP requests, bounds JSON bodies, and serves the three allowlisted local assets. Calling `createServer()` does not listen on a port. Tests can inject `dataFile` or a store implementing `read()` and `mutate(operation)`.
- `src/domain.js` validates records, enforces references and assignment capacity, applies deletion cascades, and computes coverage and text exports.
- `src/store.js` keeps a memory snapshot and writes each successful mutation to the workspace JSON file through a temporary file and atomic rename. Failed operations or writes leave the memory snapshot unchanged.
- `public/index.html`, `public/styles.css`, and `public/app.js` provide the plain HTML/CSS/JavaScript dashboard. Browser requests use the same-origin API; user-provided labels are rendered with `textContent`.
- `test/` contains Node's built-in test runner suites for the domain, persistence, simulated requests, real HTTP, and dashboard logic.

## Privacy and local data

Event names and locations, shift times and capacities, volunteer names, and assignments are stored unencrypted in `data/coverage.json`. There is no telemetry, analytics, remote font, external API, account system, or network integration. The default listener is restricted to this computer. Anyone who can access that listener can read and modify all records; there is no authentication or per-user access control.

The summary download includes volunteer names and event schedules. Treat both the data file and downloaded summaries as organizer records and share them deliberately. The application has no automatic retention policy. Individual records can be deleted through the API, with the cascades described above. For a backup, stop the server and copy the data file to a protected location within the workspace. To restore, stop the server before replacing the data file with a valid backup. Do not edit the file while the server is running. If startup reports corrupt storage, preserve the file and restore a known-good backup; startup does not silently reset it.

## Limitations

- Coverage measures assigned headcount. It does not check overlapping shifts, volunteer availability, skills, attendance, or confirmation. One volunteer can be assigned to overlapping shifts.
- There are no reminders, recurring shifts, calendar integrations, or automatic scheduling. Organizers must review gaps before each event.
- The dashboard supports event and shift creation/editing, volunteer creation, assignment/removal, filtering, and export. Event/shift deletion and volunteer editing/deletion are available through the API only.
- The dashboard refreshes after its own changes or a page reload; changes from another browser are not pushed live. Times are entered/displayed in the browser's timezone and stored/exported in UTC. There is no event-specific timezone setting.
- Storage is intended for small local teams: one process per data file, synchronous whole-file writes, no pagination, database locking, or automatic backups. Atomic replacement is not a guarantee against data loss from a disk or power failure.
- Browser layout and assistive-technology behavior require manual verification; the automated DOM stand-in is not a full browser.

## Acceptance walkthrough

Run the test and build commands above, then use a fresh workspace or a clearly named review event:

1. Create an event and a shift with capacity 2 and an end time after its start. Confirm two open spots appear.
2. Add two volunteers. Assign one and confirm the shift shows 1 of 2 assigned and one open spot. Assign the second and confirm it becomes fully covered.
3. Enable **Show only coverage gaps**. Confirm the covered shift disappears. Show all shifts, remove an assignment, and confirm the gap reappears.
4. Edit the event and shift. Attempt an end time before the start and confirm an error appears without saving. With two assignments, attempt capacity 1 and confirm rejection.
5. Create a second event and switch between events. Confirm counts and shifts follow the selected event while volunteers remain shared.
6. Export the summary. Confirm the downloaded text contains only the selected event's shifts, UTC times, assigned counts, open counts, and volunteer names.
7. Stop and restart the server. Confirm saved records and coverage survive. Check `http://127.0.0.1:3000/api/health` returns `{"status":"ok"}`.

The automated suites cover the core acceptance workflow and failure handling. The steps above also provide a manual browser review; passing automated tests alone does not establish visual or accessibility acceptance.
